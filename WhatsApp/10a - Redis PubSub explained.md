Two kinds of connection
phone <-> chat server: WSS (WebSocket + TLS)
chat server <-> Redis: plain TCP, RESP protocol
  (not WebSocket)

Each chat server holds
- 1 publish connection
- 1 subscriber connection
One subscriber conn carries ALL its users ^OgQksnLO

Pub/Sub properties
- nothing stored, at-most-once
- PUBLISH returns listener count
- subscriptions die with the connection
- a subscribing conn can only
  (un)subscribe and ping ^pf1dECF1

With a cluster (sharded pub/sub)
hash("user:bob") -> node 3
S1 publishes to node 3, S2 subscribes there
every server connects to every node
=> N x M connections
classic PUBLISH hits every node: avoid ^EoVMsOaN

Decision
Redis is the phone book for servers:
each server subscribes to user:{id}
for every user connected to it. ^pVq4tsVl

Why
Write to DynamoDB first, publish second.
The inbox guarantees delivery. Redis
only makes it fast. ^0gGfgTbM

If Redis drops a message

reconnect or on a periodic inbox poll.
